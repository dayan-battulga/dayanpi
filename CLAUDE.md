# dayanpi: notes for Claude Code

## What this repo is
A FastAPI dashboard for my Raspberry Pi 5 (focus tracker, stats, camera). Right now I'm building a focus tracker: the webcam sits at my desk and the site shows whether I'm working, on my phone, or away. docs/MANUAL.md explains how the app runs, and docs/ has a guide per add-on. If anything in this file disagrees with the code or the docs, trust those and tell me.

## Where things are
- All the Python lives in one package, dayanpi/, split by what it talks to: app.py (FastAPI), paths.py (STATIC_DIR, MODELS_DIR, DEFAULT_DATA_DIR, FOCUS_CHECK_DIR), hardware/ (camera, collector, voice, llm), vision/ (detector, hands, gestures, export_fixture: the browser port's fixture), focus/ (tracker, worker, stats, check, todos, days, coach, desks, browser_camera, camera_source, voice_setting, sharing), auth/ (accounts.py: the SQLite store for users, sessions, invites and Mac tokens, password hashing and the lockout; no FastAPI in it. routes.py: the APIRouter app.py includes, with every account route (login, logout, join, me, password, tokens, invites, accounts), SESSION_COOKIE, Viewer, find_viewer/read_viewer/read_bearer, the cookie helpers, TAILSCALE_LOGIN and is_from_my_devices (the one Tailscale-User-Login check, for the camera lock and the sign-in), and the `accounts` and `lockout` globals the middleware uses and tests monkeypatch), utils/ (threads, files), static/ (the dashboard's build output from web/: never edit it by hand). Import with the full path (`from dayanpi.focus.tracker import FocusTracker`), never a bare module name.
- Outside the package: web/ (the dashboard's source, see Dashboard below), design/ (the approved design: SPEC.md, mockups/, fixtures/; see Design below), models/ (ONNX files), tests/, mac_helper/, deploy/ (dayanpi.service, dayanpi.env.example), docs/ (MANUAL.md for setup and running, plus one guide per add-on: focus-tracker.md, pi-camera.md, voice.md), and the gitignored data/ and focus_check/ written on the Pi. pyproject.toml sets pytest's testpaths and pythonpath, so plain `pytest` from the repo root works.
- A new module goes in the package folder that matches what it talks to; a new thing you run by hand gets a main() and runs with `.venv/bin/python -m dayanpi.<module>` from the repo root, like dayanpi.focus.check and dayanpi.focus.stats. Nothing that imports the package goes at the repo root.

## How it runs
- Code gets pushed to main, either by you from a cloud session or by me from my Mac. I pull on the Pi at ~/Desktop/site-page/dayanpi and run `sudo systemctl restart dayanpi`.
- uvicorn serves `dayanpi.app:app` on 127.0.0.1:8000 under systemd (deploy/dayanpi.service, runs as user dayoon; a change to that file needs `sudo cp deploy/dayanpi.service /etc/systemd/system/` and `sudo systemctl daemon-reload` on the Pi). Tailscale Serve/Funnel exposes it at https://dayoon.tail279594.ts.net.
- Accounts: dayanpi/auth/ keeps users, sessions, invites and Mac tokens in SQLite at data/accounts.db (find_data_dir(), so DAYANPI_DATA_DIR moves it; stdlib sqlite3, one connection, one threading.Lock around every use, PRAGMA foreign_keys=ON so removing a user cascades to its sessions and tokens; ids are AUTOINCREMENT, so a removed account's, token's or invite's id never comes back for the next one). At most 4 accounts: the owner (me) and members. Passwords are hashlib.scrypt (n=2**14, r=8, p=1, 16-byte salt per user) stored as "scrypt$16384$8$1$salt$hash" and compared with hmac.compare_digest; sessions, invite codes and tokens are random and stored only as sha256 hex. Never log a password, session, invite code or token: invite codes only ever sit in the /join/<code> page path, and app.py's filter on the uvicorn.access logger rewrites that to /join/…. QuietAccessFilter, next to it, drops the lines that come every second while the room is open: GET /api/people/<name>/picture (200 and 404), POST /api/track/reading that worked, and every 429 (the limits write their own line a minute); everything else stays.
- Every HTTP route sits behind the session middleware in dayanpi/app.py (Basic Auth is gone). The cookie is __Host-dayanpi_session (HttpOnly, Secure, SameSite=Lax, Path=/, no Domain, 30 days; refreshed on use once it was last extended over an hour ago, so the DB isn't written every request). No session: /api/* and /video* get 401 {"detail": "sign in first"}, other GETs a 303 to /login?next=<path>, anything else 401. Public without a session: GET /login, /join/<code>, /api/health and /assets/* (no ".." or backslashes), and POST /api/login, /api/join, /api/logout, matched exactly. /login, /join/<code>, /settings, /me, /pi, /people/<username>, /track, /track/test and /sign serve static/index.html (app.page, a new client route needs its line there and a row in tests/test_app.py's ACCESS); / still comes from the StaticFiles mount, and the page shows the Room there. The middleware does not run for WebSocket connections, so app.WebSocketGate (outermost) closes every handshake with 1008 before the routes; don't add WebSocket routes.
- Writes must be JSON: before auth, any POST/PUT/PATCH/DELETE whose Content-Type isn't exactly application/json gets 415 {"detail": "send JSON"}, so a plain form on another site can't post (that's the CSRF guard, and it covers login, join and logout too). Right after that, a write with Transfer-Encoding, no numeric Content-Length, or one over app.MAX_BODY_BYTES (64 KB) gets 413 {"detail": "too big"} (is_body_small), so a bigger write or an upload route needs that cap raised. The page sends a JSON body on every write, "{}" when there's nothing. app.refuse_invalid_request replaces FastAPI's 422 with where and what was wrong, never the value sent: the default echoes a password back, and a lone surrogate or NaN turns it into a 500 whose traceback logs the body. Keep it for every new model.
- Everyone has their own desk (study room step 3): focus/desks.py's Desk holds one account's FocusLog, FocusTracker, TodoList, MacTrackingSetting, CameraSourceSetting, BrowserCamera (focus/browser_camera.py) VoiceSetting (focus/voice_setting.py: bedtime and voice output), SharingSetting (focus/sharing.py: what the room sees), SeatSetting (focus/sharing.py: seat.json {"hidden"}, see The room and sharing; those five are utils/files.JsonSetting, one small JSON file each, saved whole when something changes), seen_at (the stream's last tick, memory only), last_nudged ({by, at}, memory only), picture ({jpeg, at}, the seat's latest small picture, memory only, never on disk), last_spoken and its lazily made TodoCoach (app.find_coach), all in data/users/<username>/ (focus_log/, todos.json, days/, mac_tracking.json, camera_source.json, voice.json, sharing.json, seat.json; DAYANPI_DATA_DIR moves data/; usernames can't change, so neither does the folder; accounts.db stays in data/). app.desks (Desks, by username) opens one per account at startup, on join (routes.on_join) and on first use (find_desk(request), the viewer's own, a Mac token's account's); routes.on_remove moves a removed account's folder to data/users/removed/<username>-<date>[-N]/, never deleted, so the same username starts empty ("removed" is a reserved username). The first start with desks moved my old data/focus_log, todos.json, days and mac_tracking.json into my folder (desks.move_owner_data: renames only, once, one log line; if anything is in both places it moves nothing and logs an error). Only my desk (app.owner_desk) can have the Pi's cameras, and only my desk can have the Pi's speaker (study room step 5: everyone's peace sign speaks with their own coach and bedtime, on the speaker or their own page, see focus/coach.py and hardware/voice.py below). Where a desk's checks come from is app.find_camera_source: "pi" for mine unless I picked the browser (Settings → Camera, focus/camera_source.py, camera_source.json), "browser" for everyone else's, always. Where its seat picture comes from is app.find_picture_source: my pick in Settings → Camera's "Room picture from" (camera_source.json's "picture"; null follows find_camera_source), "browser" for everyone else's. A browser desk is fed by the camera in the app (study room step 4 part 2, see Focus tracker); build_desk_status gives every desk but mine NO_CAMERA (no overlays or voice), plus enabled true, camera_source, camera_paused and the desk's own gesture when it's on the browser; spoken comes off each desk's own last_spoken. Every desk route (/api/focus, /api/todos and its changes, /api/days, /api/days/<day>, /api/apps, /api/mac/app, /api/mac/tracking) answers for the viewer's own desk; snapshot_producer builds latest_focus (every desk's status by username) and latest_room (app.build_room: everyone's seat through sharing.build_seat) once a second next to latest_snapshot (the Pi's numbers), and each stream sends its viewer their own desk's focus and the room, plus the Pi's numbers for me. day_page_writer writes every desk's missing pages (write_day_pages).
- Members change their own account and their own desk; everything else is mine. Default deny: a member's POST/PUT/PATCH/DELETE (session or token) is a 403 unless "METHOD /path" fullmatches app.MEMBER_WRITES (PATCH /api/me, POST /api/me/password, POST /api/tokens, DELETE /api/tokens/<id>, POST /api/todos, PATCH and DELETE /api/todos/<id>, POST /api/mac/app, POST /api/mac/tracking, POST /api/track/reading, /api/track/pause and /api/track/source (the handler refuses a member's "pi"), POST /api/voice and /api/voice/test (POST /api/voice refuses a member's output "pi"), POST /api/sharing, POST /api/nudge, POST /api/room/hide and /api/room/show; /api/logout is in PUBLIC_WRITES, so it never gets that far), and owner-only reads are a second short list (OWNER_READS: /api/stats, /api/invites, /api/accounts). So a new write route is owner-only unless someone adds a "METHOD /path" alternative to MEMBER_WRITES; a bare path never matches. Handlers still check "own" (someone else's token is a 404). /api/stream works for members but each event carries only their own desk's "focus", no Pi stats, and every stream re-checks its session each tick and ends when it's gone (signed out, account removed).
- The room and sharing (study room step 6; docs/focus-tracker.md "The room and sharing" and "Seeing the others"): focus/sharing.py's share_parts(sharing, parts) is the ONLY gate for anything about another person: every part is a key in NEEDS with the switches it needs (a key missing from NEEDS is a KeyError), and a part whose switches aren't all on is never even made. Anything new that shows another person's data goes through share_parts with its own NEEDS line, and no route hands out anyone else's whole desk. Each desk's SharingSetting (sharing.json, DEFAULT_SHARING: focus, todos, history, nudges on; apps, sites, video off; plus "lamp", one of sharing.LAMP_COLORS teal/green/sky/yellow/pink/white, teal by default, POST /api/sharing {lamp} only those six. The page puts it on every element that draws someone's lamp as data-lamp (seats, here-faces, Settings' preview, the peek, the rail and bar, their desk, the desk sign and its lamps): dashboard.css's [data-lamp] rules set --focus-lamp from the theme's --lamp-<color> (next to --work/--phone/--away; both shades 3:1 on --bg and --surface, kept off the phone and away hues, web/src/styles/lamps.test.ts), and only the working rule reads it, so phone and away look the same for everyone) is set by POST /api/sharing (StrictBool fields, extra forbidden), whose reply has the desk's seat built the same way (Settings' preview). Here = sharing.is_here: the stream open (Desk.seen_at, set by event_stream each tick) or a check with a frame (status last_check.at) within HERE_S (120 s), so my desk is always here while the Pi's camera runs. build_room is every account's seat, oldest first, the same for every viewer; the page puts yours first. Nudges (POST /api/nudge {username}): sharing.can_nudge on the target's seat (phone NUDGE_AFTER_S 5 min, nudges on, wait_s 0); yourself is a 400, can't be nudged a 409, within NUDGE_EVERY_S (10 min, per target, from anyone, Desk.last_nudged) a 429 with Retry-After; it goes through speak_to(desk, "<name> says put the phone down", now, kind="nudge"), so the Pi's speaker for my desk and a clip for everyone else's, and last_spoken carries kind (the page shows a nudge as a toast, never the peace pill). Hiding a seat: POST /api/room/hide and /api/room/show {username} (PersonRequest, the nudge's too), anyone signed in, set_seat_hidden: yourself is a 400, hiding someone here a 409, one journal line each ("sam hid dayoon's seat"). It's the desk's SeatSetting, and seat_desk clears it whenever it finds them here, so build_room brings the seat back within a second; the seat stays in the stream with "hidden": true and RoomPage leaves it out (never your own, since your first stream event can come from a room built before you were here) while it still counts toward ROOM_SIZE, so it's never an open seat; the sidebar and bottom bar only ever list people who are here. The × is SeatCard's .seat-hide on someone else's seat that isn't here, hooks/useSeatHiding holds the change through useHeldReply and toasts Undo (Toaster's .toast-action). Fixture Room-offline (Alex offline; --hover=.seat-hide shows the ×, --click=.seat-hide the toast). Seat pictures (study room step 7, focus/pictures.py, docs/focus-tracker.md "The seats' small pictures"): 640x360 JPEG at quality 60 (about 20 KB; the smallest of 0.6/0.7/0.8 that looked sharp on a seat at 2x), the same constants in web/src/lib/track.ts. A browser desk's comes as TrackReading.picture (base64, at most PICTURE_MAX_BASE64, and a reading with it still fits MAX_BODY_BYTES; read_browser_picture keeps only a real JPEG of at most PICTURE_MAX_WIDTH x PICTURE_MAX_HEIGHT (the picture's own size) and PICTURE_MAX_BYTES 44 KB, its size read from the header by read_jpeg_size before cv2 decodes anything (cv2 allocates whatever the header claims; read_jpeg_size walks the markers to the first SOS the way libjpeg does and gives up on anything libjpeg could read another way, so both always see the same one SOF), else drops it and the reading still counts), sent only while describe_tracking's send_picture (wants_browser_picture: the desk's picture source is the browser, video on and state in AT_DESK_STATES; a reading only keeps or clears the picture when the picture source is the browser) said so; mine is app.take_owner_picture in snapshot_producer: the picked Pi camera's latest_frame (app.find_picture_camera: camera_source.json's "pi_camera", "front" by default, POST /api/track/source {"pi_camera"} owner only; "side" only while is_side_camera_running, side_stream there and CameraStream.frame_age_s within SIDE_FRESH_S 3 s, else the front, and the status's side_camera_running greys Side out in Settings) through shrink_frame, only while my picture source is the Pi (even while the browser tracks me: the streams keep capturing), video is on and I'm at the desk. Tracked by the Pi with the picture from the browser, my seat's camera runs picture-only (cameraTracker's findCameraMode "picture": tracker.worker.ts with pictureOnly, no models) and POSTs /api/track/picture {picture: base64 or null} once a second, owner only (not in MEMBER_WRITES), 409 unless find_picture_source is "browser", kept through keep_picture against the Pi's state like a reading's picture, its reply {state, send_picture}. app.keep_picture stores it only with video on and at the desk, else clears it; POST /api/sharing with video off and /api/track/pause clear it at once. GET /api/people/<username>/picture serves the JPEG through share_parts' picture part (find_fresh_picture: video, here, at the desk, at most PICTURE_MAX_AGE_S 3 s old), no-store and nosniff, else 404. The camera lock and /video stay exactly as they were: the small picture is a separate copy the person turned on.
- Invites: the owner makes them in Settings; one-time, 7 days, and none work once there are 4 accounts. The join API takes the code in its JSON body and turns away a code that doesn't work before the scrypt (Funnel lets anyone guess); using the invite, the 4-account check and making the user happen in one transaction under the store's lock.
- Wrong passwords: auth.accounts.LoginLockout counts misses per lowercased username, unknown ones too; misses 1-4 are free, the 5th starts a 30 s wait that doubles after each later miss up to 15 min, tries during a wait are refused without checking. A miss is the same 401 "wrong username or password" for every name, and unknown names still run scrypt on a dummy hash; while a wait is on (from the miss that starts it) it's a 429 "too many tries, wait a bit" with Retry-After (LoginLockout.wait_left), which says nothing about the name either, since unknown names wait the same way. It's in memory, so a restart clears it. Each name is kept under its own 64-bit blake2b hash (LOCKOUT_NAME_BYTES = 8) keyed with a random key made at startup, so a sign-in only ever clears its own name's misses. It used to be 65536 shared buckets, but a quick 429 told strangers which names shared the owner's bucket, and a member with such a name could clear the owner's wait by signing in (Claude Security F5); with 64 bits nobody can find one. The map stays small because a name nobody has tried for LOCKOUT_FORGET_S (6 h) is forgotten (an OrderedDict by last attempt, dropped from the front), and only by time: never evict names because others came in, or a flood of new names resets an escalated wait. A sign-in where routes.is_from_my_devices() is true skips it entirely (check_sign_in(from_my_devices=True)): no wait, no miss counted, and a success doesn't clear what strangers ran up; with DAYANPI_TAILSCALE_LOGIN unset nothing skips. Every scrypt (hash or check) goes through routes.run_scrypt_work, two at a time on its own scrypt_pool (16 MB each), never on the event loop or the shared thread pool; a sign-in from my devices runs on my_scrypt_pool (one thread of its own), so 3 at once at most. Strangers (every sign-in not from my devices, friends over Funnel too) share routes.stranger_sign_ins (2 a second, 10 at once), taken before the scrypt: past it the same 429 TOO_MANY_TRIES with Retry-After: 1 for any name, and "turned away N strangers' sign-ins in the last minute" once a minute. The password change has its own wait, routes.password_lockout (429 "too many tries, wait a bit"), so strangers missing at /api/login can't block it; each wrong current password also counts toward the sign-in's.
- Mac tokens (dpi_..., made in Settings, shown once, revocable, at most accounts.TOKENS_MAX = 10 per account, counted in create_token's own transaction; the 11th is a 409 "10 tokens is the most. Delete one first."; create_token takes the caller's session hash and looks the session up in that same transaction, so a request that outlives its session gets a 401, never a token; a password change deletes all of the account's tokens in its own transaction, so the Mac helper needs a new one after it) go in Authorization: Bearer and only count on paths under /api/mac/, where the cookie is ignored; a Bearer header anywhere else is a 401. A token acts as its user (a member's token still gets 403 on POST /api/mac/app) and never opens /video. The helper keeps it in the same Keychain item the password used to be in (service dayanpi, account DAYANPI_USER) and sends it with add_unredirected_header, so urllib never forwards it on a redirect.
- Limits are per account or per kind of caller, never per IP (slowapi is gone: it sat behind the auth middleware, so it only ever throttled me, and behind Tailscale every request shares 127.0.0.1), all in memory through utils/limits.py (TokenBucket, and RefusalNote: one journal line a minute at most per key, never one per request). Writes: in guard_request after the role check, every write (not GET/HEAD/OPTIONS) from a signed-in account, mine and a Mac token's too, takes from app.write_allowances[user id] (WRITES_PER_S 5, WRITE_BURST 20); past it a 429 {"detail": "slow down"} with Retry-After and "write limit hit for <name>". Strangers' sign-ins: see Wrong passwords. Test the voice: once per VOICE_TEST_EVERY_S (10 s) per desk (Desk.voice_tested_at), else a 429 with Retry-After that Settings turns into "Wait N s, then test it again." Tests reset every limit per test in fresh_accounts, and the ACCESS test clears the write allowances per row. The expensive streams have connection caps instead: /video and /video/side allow 2 at once each and /api/stream 5 per account (threading.BoundedSemaphore in app.py, one per user id for the stream); past that they return 503. SlotResponse gives a slot back as soon as its stream ends, because a finally in the generator would wait for the garbage collector.
- Startup fails if DAYANPI_USER or DAYANPI_PASSWORD is missing (they only make the owner when accounts.db has no users; after that they're ignored unless accounts.db is gone). A missing camera doesn't stop startup: stream.start() logs a warning and the capture loop keeps retrying.
- You run in a cloud session or on my Mac, never on the Pi. You can't reach the Pi, its GPIO, or its camera. When something needs the Pi, give me the exact commands and I'll run them.

## Focus tracker
- The webcam is at my desk now, pointed at my face, hands and desk. Plan, one step at a time: (1) detector check, (2) turn detections into steady states (working / phone / away), (3) run it inside the app and log state changes on the Pi, (4) dashboard card with the current state, today's totals and a timeline, (5) extras. Steps 1-4 are done, and so are study room step 4 parts 1 and 2: the camera test and the tracker (the last two bullets of this section).
- The pieces: vision/detector.py (models), focus/tracker.py (FocusTracker state machine, DayTotals, Callouts, FocusLog, replay_day/total_day), focus/worker.py (the thread that scans a frame from each camera about once a second and feeds the tracker; it reads with frame_after() and a last frame id per camera, so a frozen camera means "no frame", never a re-scan of a stale picture, and it waits up to 60 s for systemd-timesyncd's sync file before the first check because the Pi's clock can be hours off at boot), utils/threads.py (LoopThread: the shared start/tick/stop base for the worker and the coach; a tick that raises is logged, rate-limited, and never kills the thread), focus/stats.py (CLI over a desk's log, mine by default or --user NAME, run with python -m dayanpi.focus.stats), focus/desks.py (everyone's desk, see Accounts), focus/merge.py (merge_readings: people and phones from both cameras, faces and hands from the front only, elapsed_ms is the sum; the merged boxes mix two cameras' coordinates, so only their confidences mean anything), focus/overlay.py (the latest check as boxes in 0-1 fractions of the frame, same cutoffs as the rules, built from each camera's own reading; the worker keeps them as last_overlay and last_side_overlay, build_focus_status sends them as "overlay" and "side_overlay" with age_s, the page draws each one over its own feed and drops it after 3 s (web/src/hooks/useOverlayBoxes.ts); never logged). app.py starts the worker in lifespan, restores today from the log first, puts build_focus_status() into every SSE snapshot as "focus", and serves /api/focus (status plus segments), /api/todos (GET, POST) and /api/todos/{item_id} (PATCH, DELETE), /api/days?month=YYYY-MM and /api/days/{day}, and /api/mac/app.
- The rules live as constants at the top of focus/tracker.py: person >= 0.5 for 2 checks = present; phone >= PHONE_MIN (0.6, a starting point until dayanpi.focus.check's mouse phase says otherwise; web/src/lib/track.ts has a copy for the pages) in 3 of the last 5 checks = on phone, out after 5 misses; 10 s without a person = away; 30 s without frames = unknown. The detector only keeps person, phone and mouse (each box counts only for its best class out of all 80, which keeps a mouse or TV remote from counting as a phone). Mice come from both passes (FrameReading.mice) for the mouse veto: detector.drop_mouse_phones drops a phone when a mouse box that scored at least as high overlaps it (IoU over MOUSE_VETO_IOU 0.3) or holds its center; the scan returns the model's phones, worker.read_frame applies the veto per camera before check_hands (lib/vision/worker.ts's readFrame the same), and dayanpi.focus.check shows the phone scores before and after it, per phase (working, mouse, phone, away), with a suggested PHONE_MIN. Every time-based rule takes `now` from the caller; tests drive it with fake clocks.
- The log is data/users/<username>/focus_log/YYYY-MM-DD.jsonl, one per desk (DAYANPI_DATA_DIR overrides data/). Lines: state, pickup, callout, mac_app (app, and site: a browser tab's host name or null), sample (every 30 s, with app and site; side_person and side_phone only when the side camera gave a frame), day_summary, day_start, restart. Never frames. Logs from before snacks and work blocks were removed still have snack and block lines and food/drink/side_food/block fields; replay_day, total_day, focus.stats and the day pages ignore them (tests/test_focus.py has an old log). FocusTracker.restore() rebuilds today from it after a restart (loses at most 30 s): replay_day() treats day_start like a state line and a restart line as a boundary (the open segment closes at the line before it), so a dead Pi never counts as focus time. A torn line is skipped, not fatal. _accumulate caps one update at MAX_STEP_S so an NTP clock jump adds seconds, not hours.
- focus/todos.py: TodoList, each desk's running to-do list in its folder's todos.json (the desk passes the path; saved whole to a .tmp and os.replace'd; an unreadable file is moved to todos.json.broken, never saved over). One current item collects seconds via track(), which app.handle_focus_update calls after every check with state == "working" (same MAX_STEP_S cap as the tracker; time saves every 30 s, edits right away). Done items leave at local midnight. At most TODOS_MAX (100) items, open and done together: add() raises TodoListFull, POST /api/todos answers 409. Logs "todo" lines (action added/done/undone/current, id, text, seconds); replay_day ignores them. build_focus_status sends snapshot() as "todos".
- Sites: mac_helper/dayanpi_mac_helper.py reads the active tab's URL through osascript only for Google Chrome, Brave Browser, Microsoft Edge (Chromium's window "mode" must be "normal") and Arc (window "incognito" must be false); every script checks "is running" first and fails closed, so a window it can't confirm as normal sends no site. Safari has no private-window property in its scripting dictionary and Firefox has no tabs, so both send no site (logged once). find_site keeps only the host name (lowercase, no www., punycode, no port or login) and SITE_PATTERN matches app.SITE_PATTERN, so the Pi never 422s a site the helper sends. The helper posts {"app", "site"} when either changes (same heartbeat and backoff); /api/mac/app takes site as optional (max 253, plain host name pattern). tracker.record_app(app, now, site) logs a mac_app line when either changes and puts site on samples and the status; days.count_mac_seconds counts SAMPLE_LOG_INTERVAL_S per sample toward its app while working or phone, the app isn't Locked and tracking isn't paused (top 10, the page's Apps section), and toward YouTube when the site is youtube.com or a subdomain (Totals and youtube_minutes); no other site is counted. tracker.MAC_STALE_S (150 s, the helper heartbeats every 60 s) clears the current app and site when the helper goes quiet, so a sleeping Mac neither shows nor counts. Never full URLs, paths, queries or titles.

## Ground rules
- You can commit and push to main. One commit per step, with a message that says what changed, and only after the tests for what changed pass. Finish with the list of changed files.
- One step at a time. Stop when a step is done and wait for me.
- No calls to outside services or endpoints unless I explicitly say so for that run.
- Code style for new code: noun-first class names, verb-first function names, one return per function, no tuple returns, repeated code goes in a utils module, descriptive names for returned values, comments only for real traps. The existing code (app.py, hardware/camera.py, hardware/collector.py) doesn't all follow these; don't refactor it to match unless I ask.
- Finish every step with the tests you ran (only the ones covering what changed) and their results, plus the exact commands for me to test it on the Pi.
- Write docs (like docs/MANUAL.md) in plain, casual language.
